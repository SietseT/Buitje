# Buitje

A modern precipitation radar for the Netherlands (a fast, ad-free alternative to buienradar.nl), built on KNMI's public radar data.

## Architecture

- `apps/backend` — Fastify + TypeScript (Node, ESM). Polls the KNMI Open Data API every minute, parses the HDF5 radar composite, reprojects it, colorizes it to PNG, and serves it.
- `apps/frontend` — Vue 3 + Vite + shadcn-vue (Tailwind v4) + MapLibre GL. Full-screen map with a scrub/play timeline over recent frames.
- pnpm workspace monorepo. Single Docker image serves both (backend serves the built frontend `dist/` as static files in production).

Data source: KNMI's `radar_reflectivity_composites` v2.0 dataset (files `RAD_NL25_PCP_NA_<YYYYMMDDHHmm>.h5`), **not** the raw per-station volume datasets — KNMI already publishes the merged nationwide composite, so there's no need to combine Den Helder/Herwijnen data manually.

## Commands

```sh
pnpm install
pnpm dev:backend     # apps/backend, http://localhost:3000
pnpm dev:frontend    # apps/frontend, http://localhost:5173 (proxies /api)
pnpm build           # builds frontend then backend
docker compose up --build
```

Backend needs `apps/backend/.env` with `KNMI_API_KEY` (see `apps/backend/.env.example` — it already contains KNMI's public anonymous demo key).

## Non-obvious things worth knowing before touching this code

- **KNMI's row/col pixel-offset sign convention is asymmetric.** Empirically verified against real files (see `apps/backend/src/knmi/reproject.ts`): `col = (x - columnOffset) / pixelSizeX` but `row = (y + rowOffset) / pixelSizeY` — note the `+`, not `-`. Using `-` for both (the "obvious" symmetric guess) silently produces a vertically-offset-by-~7300-rows image. If you ever touch the reprojection math, re-verify against a real downloaded file's `geo_product_corners` attribute rather than trusting the KNMI HDF5 spec PDF alone. `reproject.test.ts` pins this exact `+`/`-` behavior via the extracted `sourceRowCol` helper — run `pnpm test` (in `apps/backend`) after touching it.
- **The output PNG's rows are spaced evenly in Web Mercator y, NOT in latitude.** `RadarMap.vue` hands each frame to MapLibre as an `image` source pinned by its four corner lon/lats, and MapLibre stretches the image linearly in *Mercator* space. A plain equirectangular (linear-in-latitude) grid therefore lands its corners correctly but displaces everything in between towards the pole — up to ~16 km too far north around the middle of this grid, i.e. right over the Netherlands. Longitudes are unaffected (Mercator x *is* linear in longitude), so the symptom is a purely north/south offset that's easy to misread as a reprojection sign bug. `reproject.ts:latAtRowFraction` does the Mercator row spacing and `reproject.test.ts` pins it. If the frontend ever stops using a corner-pinned `image` source (e.g. switches to a raster tile source or a globe projection), revisit this.
- **Frame timestamps are UTC.** The `YYYYMMDDHHmm` string extracted from filenames (`apps/backend/src/knmi/parseRadar.ts:extractTimestampFromFilename`) is UTC, confirmed against the KNMI API's `created` field. The frontend (`Timeline.vue:formatTime`) parses it with `Date.UTC(...)` and renders via `toLocaleTimeString` so it displays in the viewer's local timezone — don't reintroduce a plain substring slice, that silently shows UTC instead of local time.
- **Server performance matters — every API response needs a deliberate `Cache-Control` header, not a default.** `apps/backend/src/routes/frames.ts` sets one per-endpoint based on actual freshness needs: `GET /api/frames` gets a short `public, max-age=30` (just dedupes near-simultaneous polls without risking a newly-arrived frame being hidden), `GET /api/frames/bounds` gets a full-day cache (fixed KNMI grid geometry, effectively static), and `GET /api/frames/<timestamp>.png` gets a 5-minute `immutable` cache (a given timestamp's PNG never changes once generated). This is a small single backend instance serving a public map — an endpoint with no/blanket caching gets refetched on every poll, tab, and reload, which adds up fast. Apply the same discipline to any new data endpoint (e.g. a future lightning-strikes endpoint): pick the cache lifetime from how often the underlying data can actually change, don't just copy a default.
- **This app uses a dedicated personal KNMI API key, not the shared anonymous demo key** — the old shared key was rate-limited to 50 req/min across ALL anonymous users, which is why earlier versions of `poller.ts` spaced backfill requests ~1.5s apart. That budget no longer applies, so backfill instead downloads several missing frames concurrently (`config.cache.backfillConcurrency`, default 8, env `BACKFILL_CONCURRENCY`). `apps/backend/src/knmi/client.ts`'s retry-with-backoff (respects `Retry-After`) is kept as a general safety net for occasional 429s, not as a load-bearing rate-limit calculation.
- **Backend backfills history on startup and every poll** (fetches the last `MAX_FRAMES` files, newest first, and downloads whichever aren't already cached) so the timeline isn't empty for 2 hours after every restart, and a gap from a failed/delayed tick self-heals on the next one. Newest-first + concurrent means the current frame shows up almost immediately on a cold start, with older history filling in alongside it. Restarting the backend in dev re-runs this backfill each time (`tsx watch` will do this on every source save).
- **KNMI's own `visualisation1/color_palette` in the HDF5 file was deliberately not used.** It's a grayscale/red hazard-style palette, not the smooth blue→green→yellow→red→purple gradient users expect from a rain radar. `apps/backend/src/knmi/colorize.ts` defines its own color ramp from calibrated dBZ values instead.
- **The color ramp is duplicated in two places** — `apps/backend/src/knmi/colorize.ts` (`STOPS`, generates the actual PNG) and `apps/frontend/src/components/Legend.vue` (`STOPS`, renders the on-map legend gradient). No shared package between the two apps, so if you change one, update the other too. `colorize.test.ts` pins the current `STOPS` values (exact RGBA at each breakpoint) — if you intentionally change the ramp, update both `Legend.vue` and the test's expected numbers in the same change.
- **Smooth vs. hard (stepped) color transition is a per-user browser preference, not a server setting.** `dbzToRGBA`'s `smooth` param (default `true`) is used to generate and cache **both** variants of every frame — `FrameStore`/`diskFrameStore.ts` store `pngSmooth`/`pngHard` per timestamp (on disk as `<timestamp>-smooth.png` / `<timestamp>-hard.png`), and `poller.ts` colorizes each frame twice. `GET /api/frames/<timestamp>.png` picks between them via a `?smooth=true|false` query param (defaults to smooth). The frontend's choice lives in `localStorage` (`useSmoothColorRamp.ts`, key `buitje:smooth-color-ramp`, default `true`), toggled via `ColorRampToggle.vue` in the controls menu; `RadarMap.vue` appends `?smooth=...` to every frame URL it requests and watches the preference so flipping it live re-fetches the current frame immediately (the distinct query string also busts the PNG route's 5-minute immutable `Cache-Control`), and `Legend.vue` reads the same ref to keep its gradient in sync. There's no backend-wide toggle or `/api/config` endpoint anymore — that approach was tried and superseded by this one.
- **`apps/backend` has a test suite** (`pnpm test`, run from `apps/backend`) using Node's built-in test runner via `tsx --test` — no extra test framework dependency. Currently covers the two riskiest pieces of math: the reprojection sign convention and the color ramp interpolation (see the two bullets above).
- **`frameStore` (`apps/backend/src/cache/frameStore.ts`) is an interface.** `index.ts` currently wires up the disk-backed implementation (`createDiskFrameStore`, `apps/backend/src/cache/diskFrameStore.ts` — PNGs under `.data/frames/<timestamp>.png`); an in-memory ring-buffer implementation also exists in `frameStore.ts` itself. Both honor the same interface, so swapping is just an `index.ts` change, not a caller rework.
- **The backend crashes on purpose on an unexpected error.** `index.ts` registers `process.on('unhandledRejection'/'uncaughtException', ...)` that log and `process.exit(1)` rather than trying to keep running in an unknown state. This is intentional and pairs with `docker-compose.yml`'s `restart: unless-stopped` and the `Dockerfile`'s `HEALTHCHECK` (hits `/api/frames`) — together they mean a wedged or crashed container gets cleanly restarted instead of silently hanging. Don't remove the crash handlers without also reconsidering the healthcheck/restart policy.
- **The frontend tolerates a temporarily-unreachable backend.** `useRadarFrames.ts` catches `/api/frames`/`/api/frames/bounds` fetch failures instead of letting them reject — previously a failed *initial* fetch would permanently break playback until a manual reload, since the code after the rejected `Promise.all` in `onMounted` never ran. It now exposes a `connected` ref (shown as a banner in `App.vue`) and retries every 5s until reconnected. Separately, `RadarMap.vue`'s `GeolocateControl` sets an explicit 10s `timeout` — the Geolocation API defaults that to `Infinity`, so without it a stalled location fix hangs forever with no feedback.
- **The basemap is OpenFreeMap ("Liberty" style), not CARTO.** CARTO's raster basemap tiles (`basemaps.cartocdn.com`) were used briefly, but CARTO's own docs state free basemap use requires being a registered "grantee" — not clearly free for an anonymous hobby app. OpenFreeMap's docs explicitly state no limits, no registration, no API keys. If a different look is wanted, only switch between OpenFreeMap's own styles (`positron`, `liberty`, `bright` confirmed working at `https://tiles.openfreemap.org/styles/<name>`) — don't reach for CARTO or another provider without re-checking its actual terms first, not just what search results/training data imply.
- **Local dev environment quirk (this machine, not the project):** `corepack pnpm` fails with a signature-verification error (`Cannot find matching keyid`) on this machine — unrelated to the project. Workarounds used: pin `"packageManager"` in package.json, and when running the `shadcn-vue` CLI, prefix with `COREPACK_INTEGRITY_KEYS=""` if it tries to shell out to corepack again.
- **Never do visual verification of the frontend yourself** (no launching a browser, screenshotting, or driving the dev server to "check" a UI change) — always ask the user to verify visually instead.
- Frontend path alias `@` → `src/` (Vite + tsconfig `paths`, no `baseUrl` — TS 6+ deprecated `baseUrl`, dropped it rather than suppressing the warning).
- `pnpm-workspace.yaml` has `onlyBuiltDependencies: [esbuild, vue-demi]` — needed for their postinstall scripts to run under pnpm's default script-blocking.
