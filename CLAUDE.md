# Buitje

A modern precipitation radar for the Netherlands (a fast, ad-free alternative to buienradar.nl), built on KNMI's public radar data.

## Architecture

- `apps/backend` — Fastify + TypeScript (Node, ESM). Polls the KNMI Open Data API every minute, parses the HDF5 radar composite, reprojects it, colorizes it to PNG, and serves it.
- `apps/frontend` — Vue 3 + Vite + shadcn-vue (Tailwind v4) + MapLibre GL. A place panel (what the rain is doing at your spot, plus a 2-hour history chart) beside a map card and a timeline bar; below `lg` the panel becomes a bottom sheet over a full-bleed map.
- pnpm workspace monorepo. Single Docker image serves both (backend serves the built frontend `dist/` as static files in production).

Data source: KNMI's `radar_reflectivity_composites` v2.0 dataset (files `RAD_NL25_PCP_NA_<YYYYMMDDHHmm>.h5`), **not** the raw per-station volume datasets — KNMI already publishes the merged nationwide composite, so there's no need to combine Den Helder/Herwijnen data manually.

## Commands

```sh
pnpm install
pnpm dev:backend     # apps/backend, http://localhost:3000
pnpm dev:frontend    # apps/frontend, http://localhost:5173 (proxies /api)
pnpm build           # builds frontend then backend
docker compose up --build
```

Backend needs `apps/backend/.env` with `KNMI_API_KEY` (see `apps/backend/.env.example` — it already contains KNMI's public anonymous demo key).

## Non-obvious things worth knowing before touching this code

- **KNMI's row/col pixel-offset sign convention is asymmetric.** Empirically verified against real files (see `apps/backend/src/knmi/reproject.ts`): `col = (x - columnOffset) / pixelSizeX` but `row = (y + rowOffset) / pixelSizeY` — note the `+`, not `-`. Using `-` for both (the "obvious" symmetric guess) silently produces a vertically-offset-by-~7300-rows image. If you ever touch the reprojection math, re-verify against a real downloaded file's `geo_product_corners` attribute rather than trusting the KNMI HDF5 spec PDF alone. `reproject.test.ts` pins this exact `+`/`-` behavior via the extracted `sourceRowCol` helper — run `pnpm test` (in `apps/backend`) after touching it.
- **The output PNG's rows are spaced evenly in Web Mercator y, NOT in latitude.** `RadarMap.vue` hands each frame to MapLibre as an `image` source pinned by its four corner lon/lats, and MapLibre stretches the image linearly in *Mercator* space. A plain equirectangular (linear-in-latitude) grid therefore lands its corners correctly but displaces everything in between towards the pole — up to ~16 km too far north around the middle of this grid, i.e. right over the Netherlands. Longitudes are unaffected (Mercator x *is* linear in longitude), so the symptom is a purely north/south offset that's easy to misread as a reprojection sign bug. `reproject.ts:latAtRowFraction` does the Mercator row spacing and `reproject.test.ts` pins it. If the frontend ever stops using a corner-pinned `image` source (e.g. switches to a raster tile source or a globe projection), revisit this.
- **Frame timestamps are UTC.** The `YYYYMMDDHHmm` string extracted from filenames (`apps/backend/src/knmi/parseRadar.ts:extractTimestampFromFilename`) is UTC, confirmed against the KNMI API's `created` field. The frontend (`Timeline.vue:formatTime`) parses it with `Date.UTC(...)` and renders via `toLocaleTimeString` so it displays in the viewer's local timezone — don't reintroduce a plain substring slice, that silently shows UTC instead of local time.
- **Server performance matters — every API response needs a deliberate `Cache-Control` header, not a default.** `apps/backend/src/routes/frames.ts` sets one per-endpoint based on actual freshness needs: `GET /api/frames` gets a short `public, max-age=30` (just dedupes near-simultaneous polls without risking a newly-arrived frame being hidden), `GET /api/frames/bounds` gets a full-day cache (fixed KNMI grid geometry, effectively static), and `GET /api/frames/<timestamp>.png` gets a 5-minute `immutable` cache (a given timestamp's PNG never changes once generated). `GET /api/point` and `GET /api/lightning/<timestamp>` both use the same `max-age=30` as `/api/frames`, for the same reason. This is a small single backend instance serving a public map — an endpoint with no/blanket caching gets refetched on every poll, tab, and reload, which adds up fast. Apply the same discipline to any new data endpoint: pick the cache lifetime from how often the underlying data can actually change, don't just copy a default.
- **This app uses a dedicated personal KNMI API key, not the shared anonymous demo key** — the old shared key was rate-limited to 50 req/min across ALL anonymous users, which is why earlier versions of `poller.ts` spaced backfill requests ~1.5s apart. That budget no longer applies, so backfill instead downloads several missing frames concurrently (`config.cache.backfillConcurrency`, default 8, env `BACKFILL_CONCURRENCY`). `apps/backend/src/knmi/client.ts`'s retry-with-backoff (respects `Retry-After`) is kept as a general safety net for occasional 429s, not as a load-bearing rate-limit calculation.
- **Backend backfills history on startup and every poll** (fetches the last `MAX_FRAMES` files, newest first, and downloads whichever aren't already cached) so the timeline isn't empty for 2 hours after every restart, and a gap from a failed/delayed tick self-heals on the next one. Newest-first + concurrent means the current frame shows up almost immediately on a cold start, with older history filling in alongside it. Restarting the backend in dev re-runs this backfill each time (`tsx watch` will do this on every source save).
- **KNMI's own `visualisation1/color_palette` in the HDF5 file was deliberately not used.** It's a grayscale/red hazard-style palette, not the smooth blue→green→yellow→red→purple gradient users expect from a rain radar. `apps/backend/src/knmi/colorize.ts` defines its own color ramp from calibrated dBZ values instead.
- **The color ramp is duplicated in exactly two places — keep it that way.** `apps/backend/src/knmi/colorize.ts` (`DEFAULT_STOPS`, generates the actual PNG) and `apps/frontend/src/lib/colorRamp.ts` (`STOPS`). No shared package between the two apps, so if you change one, update the other too. `colorize.test.ts` pins the backend's values (exact RGBA at each breakpoint) — if you intentionally change the ramp, update `colorRamp.ts` and the test's expected numbers in the same change. On the frontend, every consumer (`Legend.vue`'s gradient, `RainChart.vue`'s fill, the per-place sparklines) imports from `colorRamp.ts` — don't re-declare the stops in a component, that's how it became a three-way duplication in the first place.
- **Smooth vs. hard (stepped) color transition is a per-user browser preference, not a server setting.** `dbzToRGBA`'s `smooth` param (default `true`) is used to generate and cache **both** variants of every frame — `FrameStore`/`diskFrameStore.ts` store `pngSmooth`/`pngHard` per timestamp (on disk as `<timestamp>-smooth.png` / `<timestamp>-hard.png`), and `poller.ts` colorizes each frame twice. `GET /api/frames/<timestamp>.png` picks between them via a `?smooth=true|false` query param (defaults to smooth). The frontend's choice lives in `localStorage` (`useSmoothColorRamp.ts`, key `buitje:smooth-color-ramp`, default `true`), toggled with the blend button on the map rail (`MapControls.vue`); `RadarMap.vue` appends `?smooth=...` to every frame URL it requests and watches the preference so flipping it live re-fetches the current frame immediately (the distinct query string also busts the PNG route's 5-minute immutable `Cache-Control`), and `Legend.vue` reads the same ref to keep its gradient in sync. There's no backend-wide toggle or `/api/config` endpoint anymore — that approach was tried and superseded by this one.
- **Blitzortung's WebSocket feed has two traps that both fail silently.** (1) The endpoint is `wss://ws1.blitzortung.org/` on plain **443** — *not* `:3000`, which nearly every third-party client and search result still shows but which is now closed on every relay host. (2) The subscription message is `{"a":111}`; sending `{"time":0}` opens the socket successfully and then streams nothing forever. Neither mistake raises an error — you just get an empty map, which is why `apps/backend/src/lightning/relay.ts` logs its `kept N/M` summary on a `setInterval` rather than from the message handler (a dead feed delivers no messages, so a handler-driven log would print nothing at all) and `client.ts` logs open/error/close. `ws5`/`ws6` refuse connections entirely; `ws1`/`ws7`/`ws8` work. Re-probe before changing `config.lightning.wsUrls`. The LZW decoder and strike parser are verified correct against the live feed — if strikes stop appearing, suspect the endpoint, not them.
- **The lightning overlay is opt-in and off by default** (`useLightningToggle.ts`, localStorage key `buitje:show-lightning`) — it's an unofficial third-party source, so it isn't shown to every visitor. "I don't see lightning" is therefore expected until it's switched on with the bolt button on the map rail; check that before debugging the backend. Note also that `GET /api/lightning/<timestamp>` returns a 5-minute bucket *ending* at that frame's timestamp, and the newest KNMI frame lags real time by ~5-10 min, so the freshest strikes always appear with a lag.
- **Lightning strikes are persisted, and they have to be** — `apps/backend/src/cache/diskLightningStore.ts` snapshots the strike buffer to `.data/lightning.json` every `LIGHTNING_FLUSH_INTERVAL_MS` (default 30s) and reloads it on startup, wrapping the pure in-memory `createLightningStore`. Unlike radar frames there is no backfill possible: Blitzortung's feed is live-only, so whatever is missed while the process is down is gone forever. Combined with the ~5-10 min frame lag, an unpersisted store meant the newest frame's 5-minute bucket *predated every restart*, so the map showed nothing for ~15 minutes after each one — including every `tsx watch` reload in dev, which makes lightning changes look broken when they aren't. `index.ts` flushes on SIGINT/SIGTERM and on the fatal-error path; snapshot writes go via a temp file + rename, and a corrupt or stale snapshot loads as empty rather than throwing (`diskLightningStore.test.ts` pins all of this). The `.data` dir is already a docker-compose volume, so this persists in production with no new mount.
- **KNMI's two calibration sentinels need OPPOSITE treatment, and only one of them is what its name suggests.** Real files carry `calibration_missing_data = 0` and `calibration_out_of_image = 255`. `outOfImage` is genuinely unmeasured (outside the radar's coverage). `missingData = 0`, despite the name, is what every pixel with **no detectable echo** gets — i.e. the overwhelming majority of a dry map. `colorize.ts` paints both fully transparent, which is right for the map (draw nothing either way), and that masks the distinction. It stops being maskable the moment you read a *value* rather than a colour: `apps/backend/src/knmi/samplePoint.ts` originally returned `null` for both and a normal dry day came back as 24 empty frames with nothing to chart. PV 0 must read as the dry floor (`a*0+b`, i.e. the bottom of the calibrated scale), and only `outOfImage` as `null`. The zero check in `pvToDbz` is load-bearing, not defensive noise: if a future product puts the missing-data sentinel anywhere other than the bottom of the PV range, running the formula on it would invent a ~95 dBZ reading. Pinned by `samplePoint.test.ts`.
- **`GET /api/point?lat=&lon=` reads reflectivity at one coordinate over the whole cached timeline** — what the place panel's chart and the per-place sparklines are built on. It exists because the frontend only ever receives *colorized, reprojected* PNGs, so it cannot recover a dBZ value on its own. It returns one entry per frame in the same ascending order as `/api/frames`, so the two line up index-for-index. A coordinate outside the radar grid is a 200 with all-`null` values, not an error — "nothing measured here" is a legitimate answer the UI renders as a gap.
- **The PV grids behind `/api/point` live in their own store** (`apps/backend/src/cache/pvStore.ts`, `.data/pv/<timestamp>.pv.gz`), deliberately *not* in `FrameStore`. A grid is 700×765 = ~535 KB raw against a PNG's tens of KB, so loading one on every `FrameStore.get()` would slow the hot `/api/frames/<timestamp>.png` path for a value that route never uses. Gzipped they're ~256 bytes each (the grids are overwhelmingly zeros — 24 frames cost ~1.3 MB on disk vs 4.3 MB of PNGs), and decompressed copies are cached in memory so a request doesn't gunzip the whole timeline. The poller's backfill treats a frame as missing if *either* store lacks it, so an existing deployment with PNGs but no grids heals itself on the next tick rather than serving empty series forever.
- **`.data/grid.json` persists the projection + calibration, and it's load-bearing for the same reason `bounds.json` is.** The poller skips already-cached frames, so after a restart with a full cache nothing re-parses an HDF5 file — without the persisted copy, `gridInfo` would stay `null` and `/api/point` would 503 indefinitely. `loadGridInfo()` runs alongside `loadGridBounds()` in `index.ts`. Verified: restart with a full cache, zero `[poller] processed` lines, `/api/point` still answers.
- **Dark mode is a user switch, and swapping the basemap wipes every custom layer.** `useTheme.ts` (localStorage `buitje:theme`, seeded once from `prefers-color-scheme` and then never overridden by the OS again) toggles `.dark` on `<html>`; `style.css` already had the `@custom-variant` and the full `.dark` token block, so no CSS work was needed. The map swaps between OpenFreeMap's `positron` and its `dark` counterpart — stay inside OpenFreeMap here, per the basemap bullet below. **The trap:** `map.setStyle()` discards all custom sources and layers, so the radar image layer and the lightning layer have to be re-added, and `applyLocalLabelLanguage()` re-run, from the `style.load` handler — which fires on the initial load *and* after every swap, so it's the single place that does it. `setStyle` is called with `{ diff: false }` on purpose: what MapLibre's style diffing preserves between two unrelated styles isn't something to rely on. `maplibregl.Marker` instances are plain DOM and survive.
- **Controls are grouped by what they change, not by convenience.** Map rail (`MapControls.vue`, top-right on the map): zoom, locate, lightning, smoothing. Timeline bar: play, scrubber, speed, legend. Place panel/sheet: the places list and its add button. Next to the app name: theme, and only theme. There is no hamburger menu and no settings popover any more — if you're adding a control, put it with the thing it affects rather than reviving one. Note `MapControls.vue` drives MapLibre's `GeolocateControl` via `.trigger()` while `style.css` hides that control's own chrome (`:has(.maplibregl-ctrl-geolocate)`): the control stays mounted because it owns the permission prompt, the pulsing location dot and the `_updateCamera` neutering — only its button is ours.
- **Language follows the browser; there is no picker.** `useLocale.ts` reads `navigator.language` once and exposes a read-only ref. Deliberate trade-off: someone on an English-language browser in the Netherlands can no longer force Dutch. `useI18n()` still reads it as a plain ref, so making it writable again is the only change needed to bring a switch back.
- **`apps/backend` has a test suite** (`pnpm test`, run from `apps/backend`) using Node's built-in test runner via `tsx --test` — no extra test framework dependency. Currently covers the two riskiest pieces of math: the reprojection sign convention and the color ramp interpolation (see the two bullets above), plus point sampling and its calibration sentinels, the lightning LZW/strike parsing, and the stores. It also runs in CI (`.github/workflows/docker-publish.yml` gates the image build on it).
- **`config.ts` must stay side-effect free on import.** The `KNMI_API_KEY` check lives in an exported `assertRequiredConfig()` that `index.ts` calls, *not* at module scope. `relay.test.ts` imports `config` for its bounds values, and CI has no `.env`/key — a module-level `throw` there fails every test run at import time before a single test executes. Same applies to any future required-env check: add it to `assertRequiredConfig()`.
- **`frameStore` (`apps/backend/src/cache/frameStore.ts`) is an interface.** `index.ts` currently wires up the disk-backed implementation (`createDiskFrameStore`, `apps/backend/src/cache/diskFrameStore.ts` — PNGs under `.data/frames/<timestamp>.png`); an in-memory ring-buffer implementation also exists in `frameStore.ts` itself. Both honor the same interface, so swapping is just an `index.ts` change, not a caller rework.
- **The backend crashes on purpose on an unexpected error.** `index.ts` registers `process.on('unhandledRejection'/'uncaughtException', ...)` that log and `process.exit(1)` rather than trying to keep running in an unknown state. This is intentional and pairs with `docker-compose.yml`'s `restart: unless-stopped` and the `Dockerfile`'s `HEALTHCHECK` (hits `/api/frames`) — together they mean a wedged or crashed container gets cleanly restarted instead of silently hanging. Don't remove the crash handlers without also reconsidering the healthcheck/restart policy.
- **The frontend tolerates a temporarily-unreachable backend.** `useRadarFrames.ts` catches `/api/frames`/`/api/frames/bounds` fetch failures instead of letting them reject — previously a failed *initial* fetch would permanently break playback until a manual reload, since the code after the rejected `Promise.all` in `onMounted` never ran. It now exposes a `connected` ref (shown as a banner in `App.vue`) and retries every 5s until reconnected. Separately, `RadarMap.vue`'s `GeolocateControl` sets an explicit 10s `timeout` — the Geolocation API defaults that to `Infinity`, so without it a stalled location fix hangs forever with no feedback.
- **The basemap is OpenFreeMap ("Positron" style), not CARTO.** Positron was picked over Liberty for its plainer, low-contrast look, which lets the precipitation colours carry the map; it is incidentally much lighter too (55 layers / 19 symbol layers vs Liberty's ~150 / ~50). Note that switching styles can silently break `RadarMap.vue:applyLocalLabelLanguage` — every OpenFreeMap style prefers `name_en` over the local OSM `name`, but they bury that preference at different depths (Positron nests it inside a `case`/`coalesce`, Liberty did not), which is why `withLocalNames` recurses through the whole expression tree rather than matching a known shape. If labels ever come out in English after a style change, check that first. CARTO's raster basemap tiles (`basemaps.cartocdn.com`) were used briefly, but CARTO's own docs state free basemap use requires being a registered "grantee" — not clearly free for an anonymous hobby app. OpenFreeMap's docs explicitly state no limits, no registration, no API keys. If a different look is wanted, only switch between OpenFreeMap's own styles (`positron`, `liberty`, `bright` confirmed working at `https://tiles.openfreemap.org/styles/<name>`) — don't reach for CARTO or another provider without re-checking its actual terms first, not just what search results/training data imply.
- **Local dev environment quirk (this machine, not the project):** `corepack pnpm` fails with a signature-verification error (`Cannot find matching keyid`) on this machine — unrelated to the project. Workarounds used: pin `"packageManager"` in package.json, and when running the `shadcn-vue` CLI, prefix with `COREPACK_INTEGRITY_KEYS=""` if it tries to shell out to corepack again.
- **Never do visual verification of the frontend yourself** (no launching a browser, screenshotting, or driving the dev server to "check" a UI change) — always ask the user to verify visually instead.
- Frontend path alias `@` → `src/` (Vite + tsconfig `paths`, no `baseUrl` — TS 6+ deprecated `baseUrl`, dropped it rather than suppressing the warning).
- `pnpm-workspace.yaml` has `onlyBuiltDependencies: [esbuild, vue-demi]` — needed for their postinstall scripts to run under pnpm's default script-blocking.
